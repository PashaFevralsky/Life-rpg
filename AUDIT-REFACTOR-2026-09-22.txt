Life RPG — consolidated OS audit & refactor
Date: 2026-09-22
Base commit audited: 61977209c0f2fd7de890959e2c6363491e4ad0bd

SCOPE
Finance was treated as protected baseline. Refactor focuses on Work OS, Tennis OS,
Knowledge OS, Life OS and their interaction with UX7 navigation/testing.

FIXED FINDINGS

1. Dynamic OS cards did not participate in UX7 subview switching.
   Cause: cards were inserted after UX7 shell tagging and lacked class ux7-card.
   Effect: Work/Tennis/Knowledge/Life cards could remain visible on the wrong subtab.
   Fix: every dynamically injected OS card now has ux7-card.
   Covered by: source integration assertions + Playwright visibility checks.

2. Knowledge review schedule had an off-by-one error.
   Intended: immediate first review -> 1d -> 3d -> base -> 2x -> 4x.
   Actual after first review: next interval was 3 days.
   Fix: completed-review count now maps to the correct next interval.

3. Knowledge review backlog was capped at 30.
   Effect: Life OS and Knowledge OS could under-report a larger backlog.
   Fix: knowledgeReviewQueue returns the full due queue; UI still renders only a short preview.

4. Knowledge regularity compared incompatible units.
   Cause: active days in a 28-day window were compared directly with a weekly target.
   Fix: comparison now uses actual average reading days/week.

5. Knowledge month plan ignored configured reading-days/week.
   Cause: planned minutes assumed reading every calendar day.
   Fix: monthly plan-to-date scales by readingWeeklyDaysTarget / 7.

6. CRM stale threshold was inconsistent.
   Cause: Work OS quality diagnostics used configurable workStaleDays, while the original
   CRM Decision Engine always used 14 days.
   Fix: both engines now use the same configurable threshold.

7. Life Systems Score still used legacy weekly targets.
   Cause: Tennis was scored against 3 sessions/week and Knowledge against 5 days/week.
   Fix: score and explanation now use tennisWeeklyTarget and readingWeeklyDaysTarget.

8. Life OS could hide hard obligations behind the daily task limit.
   Cause: the same cap was applied to hard and soft actions.
   Fix: all hard obligations are always included. The configured 2–6 limit applies to
   the normal daily plan; exceeding it explicitly marks the day as overloaded.
